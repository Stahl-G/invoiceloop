# 三方基线比较(2026-08-04;2026-08-05 扩充)

**问题**:把每个信号当作「自动放行规则」时,静默错误 / 自动化覆盖 / 人工负载
各是什么形状 —— InvoiceLoop 的分诊是否相对 raw DWS 与简单基线构成改进
(78 评 P1;81 评修正后扩充)。

**复算**:`python3 scripts/baseline_comparison.py runs/heldout runs/heldout-workspace`
(零 API,全部从存盘证据)。

## 口径(先读,宪章六)

- **探索性,非预注册**。预注册的是 H1–H6(docs/HELDOUT.md);本表是评审后
  补做的分析,判据意义与 H 系不同。
- **偏差定义与 heldout_metrics.py / test_triage_concentration.py 完全同口径**:
  真值存在、口径争议行剔除、无 understand 入账声明或归一化后不等 = 偏差。
- **关键字段 = TIER1**(invoice_number / total_gross / total_net / total_vat /
  amount_due / seller_vat_id,搬自 dws-derisk routers.py)—— 事前存在的分层,
  不是看结果挑的。
- **InvoiceLoop 产品本身从不自动放行** —— 复核队列由人裁决。本表评估的是
  分诊信号在反事实自动放行下的质量,不是产品行为承诺。
- 「置信度阈值」= understand 的字段级 confidence ≥ 0.95 且有值才放行。
  **更正(81 评)**:此前写「DWS 不给字段级置信度」是错的 —— DWS 响应的
  `output.metadata.<field>.confidence` 存在(0.95/0.4 两档,
  `confidenceComponents.groundingScore`,`source=no-logprobs`)。正确表述:
  它是粗粒度离散的 grounding score,**不是校准正确率**;用它当「简单阈值」
  基线正合适。

## 读法(不夸大 —— 2026-08-05 按 81 评收敛)

- **三个固定点上 InvoiceLoop 在风险端最强**:TIER1 静默错误 8.98%(置信度
  阈值 16.10%,双模式 14.95%),文档静默失败 22.2%(34.3% / 31.5%),
  偏差路由召回 82.6%(55.8% / 62.8%)。但四个点互不支配 —— InvoiceLoop
  的复核负载也最高(41.8%)。
- **同预算排序质量上,分诊序与置信度升序打平**(recall@budget 逐点几乎
  相同,CI 完全重叠)。本数据集上,confidence 升序就是个强排序器;
  分诊的差异化不在排序,在**操作点的安全性**:冻结绑定、快照、审计链
  这些置信度信号给不了的东西(confidence 是抽取器自报,无独立校验)。
- **残余不是零**:分诊放行档仍有 8.98% 的 TIER1 字段静默错误 —— 产品
  形态是「人裁决队列」而非「自动放行器」,§8 限定与本表同屏有效。
- **真实人工负载另报**:反事实分诊负载 41.8% 不等于产品里人要做的操作量。
  整单放行口径下(requires_adjudication ∪ TIER1 全要点),demo 三份实测
  `decision_load_for_release` ≈ 0.83 —— 该字段在 deliverable.json summary
  里逐 run 给出。

## 不主张

- 不主张 8.98% 是「真实错误率」—— 它是 100 份留出集上、按上述口径的观测值;
- 不主张跨数据集成立(DocILE 之外的分布未测,§8 限定三);
- 不主张分诊序在排序质量上优于置信度升序 —— 本数据集上二者打平(见上);
- 不主张置信度基线无用 —— 它是曲线上合法的一点,负载更低时可选。

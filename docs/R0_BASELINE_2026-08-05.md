# R0 基线实测(2026-08-05,HAR-0001)

v0.2 设计 §14 要求:任何「41%→30%」叙事之前,先用修正后的口径重测 R0
(设计禁令 #16:禁止把 41.1% 称为 document review rate,除非实测如此)。
本文件是实测结果。**41% 不是 R0。**

复算(零 API,存盘证据):

```bash
INVOICELOOP_CORPUS=runs/heldout-workspace python3 -m invoiceloop run \
  --out <新目录> --doc-ids <100 ids>   # 或直接用 runs/heldout-r3
```

## 实测(runs/heldout-r3,100 份留出集 × 10 字段 = 1000 槽)

| 指标 | 值 | 口径 |
|---|---|---|
| mandatory field review load | **61.2%**(612/1000) | `requires_adjudication` 槽比例(分诊口径) |
| document touch rate | **100%**(100/100) | 至少一个需复核槽的文档比例 |
| decision_load_for_release | **82.3%**(823/1000) | 整单放行必须显式人裁的槽(requires ∪ TIER1),deliverable.summary 逐 run 给出 |
| TIER1-only 反事实分诊负载 | 41.8% | 仅 287 个有真值 TIER1 槽(此前三方基线表口径) |

## 「41%」的真实身份

三方基线表里的 41.8% 是 **TIER1-only、有真值子集、反事实自动放行**口径 —
— 三个收窄叠加。全槽全文档的保守策略实测是 61.2% 字段复核、100% 文档触达、
82.3% 放行决策负载。对外叙事一律用本表数字;41.8% 只允许出现在
「反事实分诊信号质量」的语境里,与同口径基线并排。

## 这组数字说明什么

- 保守策略下**每份文档都要人动手**(touch 100%)—— 这正是改进层的存在
  理由,不是羞耻数字:R0 的职责是把一切可疑的拦给人,宁可错拦;
- 改进空间真实存在:612 个需复核槽里多少是低收益软复核,由 R1 的
  cohort 统计(improve mine)回答;
- R0 的 HAR-0001 与 2026-08-05 前的内联分诊**逐字节等价**(heldout 重跑
  零 diff,tests/test_routing.py 钉死),所以本表同时是既有系统的实测,
  不是新行为。
